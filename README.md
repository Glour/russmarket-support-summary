# Сводка support: CRM + рабочие чаты

Тестовое задание на роль специалиста по AI-автоматизации. Решение помогает support увидеть срочные случаи и отделить подтверждения CRM от сведений из переписки.

**[Полный ответ на задание →](Решение.md)** · **[Пример автоматически сформированной сводки →](demo.md)** · **[Пилот и риски →](Пилот-и-риски.md)**

## Быстрый запуск

Нужен Python 3.9 или новее, внешние библиотеки и ключи не нужны:

```bash
python3 solution.py example.json
python3 solution.py example.json --format json
python3 -m unittest -v
```

Пример содержит синтетическую дату и условное время обновления CRM. `as_of`, `deadline` и `crm_updated_at` задаются с часовым поясом ISO 8601; даты первого и последнего рабочего дня сравниваются с календарной датой `as_of` в указанном для неё часовом поясе. Для пилота в `as_of` следует использовать часовой пояс бизнес-процесса. При отсутствии времени обновления CRM, данных старше 24 часов или отметке времени в будущем случай получает предупреждение и приоритет не ниже ручной проверки; 24 часа — демонстрационное значение, требующее согласования.

## Как работает

Правила определяют приоритет по полям CRM. Для П-08 также показан вручную извлечённый сигнал из сообщения курьера: ещё до срока он поднимает риск в очередь срочных; это сообщение не подтверждает изменение CRM. Для каждого случая выводятся исходные данные, следующее действие и предупреждения. Некорректная карточка не прерывает обработку остальных: она попадает в ручную проверку. Отмеченное вручную противоречие также направляется на проверку. Если некорректны общие данные или файл недоступен, команда завершается с ошибкой, не выдавая неполную сводку за полную.

Публичный пример не обращается к CRM, чатам или ИИ и не обновляет статусы. Разбор свободного текста, автоматическое выявление противоречий и надёжная привязка сообщений к карточкам не реализованы: в примере данные подготовлены заранее. [Инструкция для возможного извлечения с помощью ИИ](AI-извлечение.md) — проект, модель не вызывалась. Источники, политика свежести, права доступа, проверка качества извлечения и интеграция должны быть согласованы с support до пилота. Скрипт выводит текст сообщений как есть и не обезличивает его; не следует помещать реальные персональные данные в публичный репозиторий.

## Что проверено

Шестнадцать локальных тестов покрывают случаи из задания, границу времени доставки, разные часовые пояса, противоречия, свежесть данных, ошибки и дубли карточек, а также разделение чата и подтверждений CRM. Это проверка прототипа на искусственных данных; эффективность и полнота на реальных процессах не измерялись. Ответ и план пилота — в [решении](Решение.md).
